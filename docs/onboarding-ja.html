エージェントを作る。
その基盤から理解する。

Agentic Value Accelerator（AVA）を初めて触る開発者へ。全体像からローカル起動、最初の変更までをつなぐ、リポジトリの案内図です。

対象：新規参加の開発者解析日：2026-10-31静的コード解析に基づく
設計・保守の詳細：技術設計・保守ガイド 日本語版にAWS構成図、アプリアーキテクチャー、機能一覧、変更・運用・復旧手順をまとめています。
01 / PURPOSE

単一のアプリではなく、開発・運用の集合体

AVAは、AWS上でエージェントを計画・構築・保護・運用・統制するためのアクセラレーターです。Pythonのエージェントだけでなく、React管理画面、FastAPI、Terraform等のIaC、業務別サンプルを含みます。まず共通基盤のControl Planeを理解し、担当するユースケースへ進むと読みやすくなります。

PLAN

何を実現するか

ビジネス価値、導入計画、アーキテクチャ指針。plan/から目的と判断軸を確認します。

PLATFORM

どう管理するか

管理画面、API、デプロイ、監視、ガバナンス。共通基盤の中心はplatform/control_plane/です。

APPLICATIONS

何を動かすか

金融向けFoundry、独立した参照実装、App Factory。業務ロジックはここから選びます。

最初に決めること：管理画面・基盤を変更するならControl Plane、共通基盤を利用して業務エージェントを作るならFSI Foundry、個別の実装例を調べるならReference Implementationsへ進みます。

03 / ARCHITECTURE

管理する仕組みと、動くエージェント

ブラウザ / React管理・設定・実行状態の確認
→
FastAPIルート → サービス → AWS連携
↓ デプロイ要求：成果物とパラメータ
S3 / Step Functionsソース保管・実行のオーケストレーション
→
CodeBuild / IaCインフラ・イメージ・UIの構築
↓ 構築された実行環境（構成はパターンによる）
AgentCore等業務エージェントを実行
→
モデル / ツールBedrock・Gateway経由のモデル呼び出し等

概念図です。すべての参照実装が同じ経路を通るわけではありません。AWSデプロイの構成はplatform/README.mdに基づきます。

ローカルでは5サービス

Composeはフロントエンド（3000）、API（8000）、LiteLLM Gateway（4000）、Redis、PostgreSQLを起動します。nginxは/api/をバックエンドへ転送し、/pingと/healthも中継します。PostgreSQLはGatewayのキー・利用額データを保持します。Control Planeのデプロイ記録はDeploymentServiceがDynamoDBへアクセスするため、PostgreSQLをRepo全体のDBと捉えないでください。

ローカル起動 ≠ AWS非接続。ComposeにはLOCAL_MODE=trueとUSE_DEV_AUTH=trueがありますが、モデル呼び出し・資産参照・デプロイなどにはAWS認証・権限・対象リージョンの確認が必要です。開発用認証の構成を本番設定として転用しないでください。
04 / FOLLOW ONE REQUEST

Foundryのデプロイ要求を追ってみる

代表例はapplications.py → deploy_foundry_use_case()です。静的な呼び出し関係と関数本体を照合しました。

1

認可と入力チェック

Operatorロールを要求し、ユースケースの存在、対応フレームワーク、デプロイパターンを検証します。

2

基盤の出力とパラメータを合成

foundation-stackの出力を解決し、リクエストの設定を重ねます。Guardrailと観測設定もここで組み込みます。

3

観測・Gateway設定を準備

条件が揃えばLangfuseプロジェクトやGateway仮想キーを準備します。Gateway準備の例外は警告に記録され、直接Bedrockを使う経路へフォールバックします。

4

デプロイ記録とソース成果物を作成

DeploymentCreateを作り、DeploymentServiceへ渡します。共通IaC、Dockerビルド用コード、ユースケースのsrc、存在する場合はUI等をZIPにまとめ、S3へアップロードします。

5

パイプラインと結果を確認

後続のオーケストレーションでCodeBuildがIaC・コンテナ・UIを構築します。APIの応答だけで完了と判断せず、パイプライン状態と出力URLを確認します。

読む順番：applications.py → services/deployment_service.py → services/pipeline_service.py → 対象foundationsのIaC。最後の2箇所は次に読む候補で、全分岐の詳細検証は本資料の範囲外です。

05 / FIRST RUN

初日は、画面とAPIの疎通まで

README記載の前提はPython 3.11以上、Node.js 22以上、AWS CLI 2.28.9以上、Terraform 1.0以上、Docker buildxです。ローカル実行にはDocker Compose v2またはFinchと、有効なAWS認証を準備します。選択したモデルに応じてBedrockアクセスや追加キーが必要です。

1. 設定と認証を用意

# Repoルートから
cd platform/control_plane
cp .env.example .env
# .envを編集し、使うモデル・AWSリージョン等を設定
# AWSプロファイルの認証を済ませる（SSO等、環境の方式に従う）

Gatewayへはホストのcredential_processがそのまま渡りません。READMEのLocal Developmentにある一時認証情報のエクスポート手順を実施してください。秘密値をコミットしないようにします。

2. UIをビルドしてからCompose起動

# platform/control_plane/ から
cd frontend
npm ci
npm run build
cd ..
docker compose up --build -d
# Finchの場合は docker compose を finch compose に置換

3. 起動確認

docker compose ps
curl -f http://localhost:8000/ping
# ブラウザで http://localhost:3000 を開く
# Gatewayは http://localhost:4000

まずUI表示とAPI疎通を確認し、その後にモデル呼び出し・AWS資産表示へ進みます。AWSデプロイはplatform/README.mdからinfrastructure/scripts/deploy-full.shの前提を確認し、アカウント・リージョン・権限を決めて実施します。

07 / TROUBLESHOOTING

詰まりやすい境界を先に知る

変更したPythonコードが反映されない

Composeはバックエンドソースをマウントしません。control_plane/でdocker compose build backendを実行後、docker compose up -d --force-recreate backendで再作成します。

UIを再起動しても古いまま

フロントのDockerfileはホストで生成済みのdist/をコピーする構成です。frontend/でnpm run buildを実行してから、control_plane/でdocker compose build frontendとdocker compose up -d --force-recreate frontendを実行します。

モデル呼び出しが認証エラーになる

AWS一時認証の有効期限とコンテナへ渡した認証情報を確認します。ホスト側で更新・エクスポートした後、Gatewayを再作成し、必要なモデルアクセスとリージョンを確認してください。

AWS資産の数が少ない・見えない

AWS_REGIONは管理基盤、GOVERN_AWS_REGIONは管理対象フリートの領域です。Composeにはテーブル別リージョンの設定もあります。アカウント・対象リージョンと設定の意味を照合してください。空の一覧だけで「資産なし」と判断しないようにします。

ヘルスチェックが404になる

基本疎通は/pingを使います。Composeのコメントでは/api/v1/healthを使わないよう案内されています。実際のルーターマウントはmain.pyで確認してください。

停止・データ保持の違い

docker compose downはコンテナを停止・削除し、名前付きボリュームは保持します。down -vはボリュームも削除するため、Gatewayの保存データを消してよい場合だけ使用します。

09 / EVIDENCE

根拠と解析の範囲

Repo全体の概要はREADME群、ローカル構成はComposeとnginx設定、UI検証コマンドはpackage.json、デプロイの代表経路はapplications.pyとDeploymentServiceを根拠に整理しています。リンクは本HTMLをdocs/に置いた状態での相対リンクです。

  • ルートREADME / Platform README / Applications README
  • docker-compose.yaml / nginx.local.conf
  • frontend/package.json / backend/requirements.txt
  • main.py / applications.py / deployment_service.py

codebase-memoryのインデックスとソースを併用し、利用した10ファイルのカバレッジを確認しました。nginx.local.confは構文解析対象外のためソースを直接確認しています。静的解析は実行時の成功を保証せず、全アプリ・全分岐を網羅した監査ではありません。ローカル起動、AWS操作、アプリのテスト実行は本解析では行っていません。Repoが更新された際は設定とソースを優先してください。
