全体像と読み方

資産を発見可能な定義にする

このrepoの中心機能は、5種類の資産をAWS Agent Registryに保存し、AVA側のポリシーと承認キューを組み合わせて登録・承認・廃止を管理することです。

構成要素責務見分けるポイント
AWS Agent Registryレコード、descriptor、AWSタグ、ライフサイクル状態の保存AWS側の実体。通常の共通クライアントは agent-registry-control を使用
Registry画面登録対象ごとの一覧、カタログからの登録、廃止/registry が入口。画面URLとAPIのprefixは異なる
Approval Policies登録時にどの扱いを選ぶかのルール/secure/approval-policies。AVA側のDynamoDBデータ
Approval Queue要求・ポリシーのsnapshot・判断履歴の保存と操作/operate/approvals。AWSレコードとは別に保存される
Govern → Agent Registryデプロイ、AgentCoreなどの複数ソースを統合してガバナンスを表示/govern/agents。デモデータを合成する実装もあり、AWS保存一覧と一致するとは限らない
「登録」の意味

名前・接続先・能力などをカタログ化する操作です。画面の Deploy to Registry も定義の登録APIを呼びます。これだけでAgent runtime、認証基盤、MCP Serverのプロセス、Skillの実行環境が作成されるわけではありません。

解析の範囲

現行の画面ルーティング、FastAPIの公開ルート、共有クライアント、承認エンジン、Terraform、成功hook、関連参照実装を照合しました。グラフの索引カバレッジも確認し、索引対象外のKYCテンプレートは直接読み取りました。実アカウントのAPI呼び出しやデプロイは実施していません。

本HTMLはオフラインで読める単一ファイルです。シミュレーターはローカルの学習機能で、AWSに接続しません。ソースリンクを開くには元のrepoのディレクトリ構造を維持してください。

レコードとデータ構造

AWSの外枠とAVAの中身

AWS側のレコード外枠に、AVA固有の情報をdescriptorのJSON文字列として格納します。資産別APIは、その値を画面向けの形に変換して返します。

識別子
recordArn と recordId。IDが返らない形ではARN末尾から補完。画面向けAPIは agent_id、server_id、skill_id、resource_id を返す
名前
AWSの name は {kind}-{sanitized-display}-{uuid8}。表示用 displayName は別フィールド。通常登録では同じ名前を再送しても同一レコード更新にはならない
descriptor
descriptors.<kind>.data にJSON文字列。共有ヘルパーが型別の dataSchemaVersion を指定。custom にはschema versionを送らない
状態
AWSの状態を status_raw で保持し、UI向けの短い status も返す
タグ
AWSリソースタグと、descriptor内の利用者指定タグ配列は別。前者は分類・自動登録の照合にも使う
バージョン
共通の新規登録では recordVersion="1"。App Factoryの別スクリプトは独自の更新・version管理を行う
構造例 / 通常のAgent登録
{
  "recordType": "AGENT",
  "name": "agent-KYC-Review-a1b2c3d4",
  "displayName": "KYC Review",
  "recordVersion": "1",
  "tags": { "ManagedBy": "AVA", "Kind": "agent" },
  "descriptors": {
    "custom": {
      "data": "{\"runtime\":\"custom\",\"runtime_ref\":\"https://example.invalid/agent\",\"capabilities\":[\"kyc\"]}"
    }
  }
}

上記は保存の形を説明する例です。AWSからの実レスポンスではありません。

descriptor指定値

agentSkillsDefinition0.1.0
customdataSchemaVersionを送らない

読取時の正規化 _hydrate()

  • createdAt・updatedAt のdatetime値をISO文字列に変換します。
  • 4種類のdescriptor枝の data をJSON解析し、dataParsed を追加します。解析失敗時は None になります。
  • recordId が欠けていてARNがあれば、末尾からIDを抽出します。

一覧取得の実装上のコスト

list_records() はページを反復し、既定100件 × 最大50ページの上限を持ちます。Agents/A2AのタグフィルターはAWSの一覧フィルターへ渡さず、取得後に全条件を照合します。タグがなければレコードARNで ListTagsForResource を追加呼び出しします。

データが増えたときの意味

最大5,000件のguardと、タグ取得による追加リクエストがあるため、大規模な全件探索や任意タグ検索をそのまま担う設計とはみなさず、件数・遅延・ページ継続の扱いを確認します。

根拠: build_record_name / create_record / list_records / _hydrate資産別の _to_ui

登録処理の詳細

通常登録APIの成功経路と失敗経路
  1. 設定とAPI権限を確認

    登録は VIEWER の権限要件。registry IDが空ならルートは503。_registry_id() は環境変数の空行・文字列 None を除いて最初の有効な行を使います。

  2. 登録ポリシーを評価

    evaluate(kind, resource_id=登録名, action="register") を実行。denyなら403で終了。auto_approveなら最終目標をAPPROVED、それ以外はPENDING_APPROVALにします。

  3. 資産のdescriptorを組み立てる

    通常Agentはcustom、MCPはmcpServer、A2AはAgentCard、SkillはagentSkillsDefinition、Customは自由JSON。タグと表示名を含めて CreateRegistryRecord を呼びます。

  4. DRAFTへの遷移を待ち、承認申請

    _wait_for_status(..., target={"DRAFT"}, timeout_s=15) を呼び、その後 SubmitRegistryRecordForApproval を実行します。

  5. 自動承認または承認キューへ

    自動承認ならPENDING_APPROVALを最大15秒待って状態変更を試行。手動承認なら enqueue_approval() で要求を保存します。

  6. 詳細を再取得して画面向けに返す

    期待した状態を固定値で返すのではなく、get_record() の結果を変換します。201の応答だけでAPPROVEDへの到達を判断しないでください。

非同期状態の待機は、どこまで保証するか

_wait_for_status() は0.5秒ごとにGetを行い、読取のClientErrorは待機中に無視します。期限切れでは例外を投げず、最後に観測した状態を返して警告を記録します。呼出元はこの返却値を使って処理を止めていません。

承認申請・自動承認の状態変更でもClientErrorをログに残して進む経路があります。そのため「申請APIを呼んだ」と「目的の状態に到達した」は別の確認事項です。

A2A: AgentCardの取得と、登録を拒否する場合

入力が agent.json で終わらない場合、.well-known/agent.json に書き換えて取得します。safe_fetch.fetch_json() に10秒timeoutとサイズ上限を渡し、JSON objectであることも確認します。

fetch guardが拒否するprivate・loopback・link-local・不正URLなどは登録を拒否します。許可されたprivate peerが必要な場合は SAFE_FETCH_ALLOWED_PRIVATE_CIDRS を担当者が検討します。一方、応答しない相手などの取得失敗では空のAgentCardで登録を続ける経路があります。レコードが存在することと、能力情報が取得できたことを区別してください。

更新と廃止の実装

MCP・A2AのPATCHは、既存descriptor内のデータを読み、指定された項目を書き換えてUpdateRegistryRecordを呼びます。登録フローと同じポリシー評価・キュー作成が自動的に適用されるとは考えないでください。

新規publishではMCPに 2025-12-11、A2Aに 0.3 を指定する一方、両PATCHルートのdescriptorでは dataSchemaVersion="1.0" が固定されています。この不一致はソースで確認した事項で、実サービスが更新を受理するかは未検証です。更新機能を採用する際は対象SDK・サービスとの互換性を確認してください。

公開DELETEルートは reg.deprecate() 経由でDEPRECATEDにします。共有クライアントには物理削除ヘルパーもありますが、ここで紹介するDELETEルートはそれを呼びません。

根拠: create_record / _wait_for_status / set_status登録・更新・廃止ルートAgentCard取得

承認ポリシーの解析

エンジンの能力と設定APIの差

ポリシーの実体はAVA側のDynamoDBです。評価エンジンは有効なポリシーを読み、kind・資産名・actionの条件が一致する候補から、優先順位が最も高い1件を選びます。

判定項目実装登録時の具体値
resource_kind* または入力kindと完全一致agent / mcp / a2a / skill / custom
resource_patternfnmatch.fnmatchcase() のglob照合。大文字小文字を区別利用者が指定した登録名。AWS側で生成されるUUID付きnameではない
action_pattern同じくglob照合register。キュー行に保存する既定actionの publish とは異なる

複数一致したときの優先順位

  1. モードの厳しさ: deny > require_approval > auto_approve
  2. resource_patternの具体性
  3. action_patternの具体性
  4. required_roleの厳しさ: ADMIN > OPERATOR > VIEWER
  5. policy_idによる決定的なタイブレーク

具体性のスコアは、* または空なら0、それ以外は「文字数 − 5 ×（*と?の数）」を最低1として計算する簡易尺度です。kindの具体性自体はscoreに含まれません。

標準の設定APIでは、3モードすべてを設定できるわけではありません

エンジンは mode を読む実装ですが、PolicyCreate / PolicyUpdate にはmode項目がありません。保存行にmodeがない場合、有効な一致ポリシーは require_approval と解釈されます。denyや明示auto_approveの分岐があることを、通常の設定画面から指定できることと同一視しないでください。

差分ソースで確認できることオンボーディングでの扱い
設定APIのkindapplication, harness, memory, mcp, a2a, identity, * を受け付けるagent / skill / custom 専用kindは標準APIで作成・更新不可。横断ルールには * を使い、名前・action条件で影響を確認
モード未指定一致した有効ポリシーはrequire_approval手動承認は有効な一致ポリシーで構成する
ポリシー未一致auto_approveを返す「設定しなければ承認待ち」ではない
テーブル未設定・読取ClientError空のポリシー一覧として扱う未一致と同じ自動承認に進む経路がある。テーブル・IAM・ログの確認が必要
ポリシー取得のページング_load_active_policies() は1回のscan応答のItemsを使い、継続キーを処理しないscan結果が複数ページになる規模では、すべてのポリシーを評価できるとは限らない
手動承認用ポリシーの例と、その適用範囲

次のJSONは POST /api/v1/approval-policies の入力例です。ADMIN権限が必要です。mode を指定せず、作成された有効な一致ポリシーを手動承認ルールとして使います。

PolicyCreate / リクエスト例
{
  "name": "Onboarding registrations require review",
  "description": "研修用の名前で始まる登録を管理者が確認する",
  "resource_kind": "*",
  "resource_pattern": "onboarding-*",

承認キューと状態

AWSとDynamoDBの2つの状態を読む
AWS / status_rawAVAのstatus意味
CREATINGpending作成処理中
DRAFTpending作成済み・申請前
PENDING_APPROVALpending承認待ち
APPROVEDactive承認済み
REJECTEDrejected拒否済み
DEPRECATEDdeprecated取消・廃止
CREATE_FAILED / UPDATE_FAILEDfailed作成・更新失敗

pending だけでは作成中・DRAFT・承認待ちが区別できません。調査では返却IDと status_raw を使います。

承認要求に保存する情報

enqueue_approval() はrequest_id、対象record ID/ARN、resource_kind=registry_record:<kind>、依頼者、理由、policy ID・名前・snapshot、必要ロール、quorum、SLA、判断配列、作成・更新・期限日時を保存します。要求テーブル未設定やput_itemのClientErrorではログを残してNoneを返します。

承認・拒否の反映

_record_decision() は要求が pending か確認し、AWS側の状態変更を試みた後、DynamoDBの判断・状態を更新します。承認はAPPROVED、拒否はREJECTED、取消はDEPRECATEDです。Identity Providerも同じ要求形式を使いますが、その実体の更新はDynamoDBで、AWS Registryの第6の資産型ではありません。

2つの状態はトランザクションとして確定しません

AWSの状態変更が失敗してもキュー行を確定する経路があります。逆にAWS変更後のDynamoDB更新が失敗することも考えられます。後者は処理順から導く障害時の可能性です。現実装ではquorumを複数人で集めず、1回の判断で確定します。既に確定した要求への再判断は409になるため、単純な再承認を復旧策にはできません。

状態を試して理解する 学習用 / AWS接続なし

通常時の呼び出しが成功する前提の説明モデルです。modeの選択はエンジンの分岐を表しており、標準設定画面の選択肢を再現したものではありません。

JavaScriptを有効にすると、条件に応じたAWS・キューの状態を確認できます。

根拠: enqueue_approval / set_status_record_decision とロール制御status変換

自動登録の別経路

共通デプロイの成功イベントから公開する

Control PlaneのTerraformは、共通のデプロイStep Functionsの成功イベントをEventBridgeからLambdaへ渡す deployment_success_hook を接続します。通常の登録APIを呼び出す仕組みではなく、Lambda自身がRegistry APIを使用します。

  1. deployment IDを抽出してDynamoDBを読む

    該当deploymentが存在し、保存状態が小文字比較で deployed の場合に続行します。IDなし・行なし・未デプロイではスキップします。

  2. 既登録を確認する

    同じ DeploymentId のAWSタグを持つレコードが見つかる場合は再作成をスキップします。通常登録のUUID生成とは異なる、デプロイ単位の重複抑止です。

  3. runtimeと参照先を出力から決める

    UI/App/Dashboard URLがあれば runtime=web-app。なければAgentCore runtime ARN、runtime ID、最後はdeployment IDを参照します。

  4. AGENTレコードを作成し、APPROVEDへの遷移を試みる

    Kind=agent、Source=foundry-deploy、DeploymentId を付与。DRAFTを待ち、申請、PENDING_APPROVALを待ち、APPROVEDに変更します。

  5. 承認済みの履歴を保存する

    キュー表に status=approved、systemの判断、policy_name="AVA Default: Application deploy auto-approves" を記録します。

比較通常の登録API成功hook
入口資産別POSTルートTerraformで指定したStep Functionsの成功イベント
ポリシー評価approval_policy_engine.evaluate()呼び出さない
承認先評価結果に応じて承認待ち / 自動承認自動承認を試みる
キュー行require_approval時にpendingで作成approvedの履歴行として作成
重複抑止生成名にUUID。再POSTは新規作成になりうるDeploymentIdタグで既登録確認
公開失敗失敗箇所によりエラー / 警告後続行handlerは例外を捕捉して ok:false を返す経路がある。履歴書込もbest effort
デプロイ成功と、公開・承認履歴の成功を分けて確認する

hookで作られたレコードはWeb UIへの参照だけの場合もあります。また、通常登録用の手動承認ポリシーがこの経路に適用されるわけではありません。履歴行もAWSの実状態を再検証してから確定する仕組みとは限らないため、AWS側の状態を照合してください。

この配線は共通Step Functionsが対象です。別のAaaS・独自スクリプト・外部パイプラインによるデプロイにまで同じhookが働くとは推定しません。重複チェックと作成も一つの原子的操作ではないため、同時イベントの扱いは別途検証事項です。

根拠: Terraformの接続handler / _already_published / _publish / _write_queue_row

参照実装の使い分け

repo内の「Registry」を区別する

App Factory: デプロイ済みruntimeの公開

applications/app_factory/scripts/publish_to_registry.py はruntimeとuse caseからAgentCard・descriptorを構築します。app-factory-<use_case_id> を名前として既存レコードを検索し、あればversionを更新、なければ作成し、承認申請を行います。

主なCLI引数は --registry-arn、--runtime-arn、--use-case-id、--region、--output-json です。成功hookの自動承認とは異なり、このスクリプトは承認申請までを扱います。Registry ID/ARN・descriptor・versionの形が通常の共有クライアントと異なるため、使用するSDKとの適合は経路別に確認します。

agentcore-in-a-box: 検索とadmission検証

LambdaのRegistry処理には read、search、curate が実装されています。searchはデータプレーンの search_registry_records(searchQuery, registryIds, maxResults) を呼び、上限を25件に抑えます。ソースの意図は承認済みレコードの検索です。検索失敗時には200応答の中の error を返す経路があるため、HTTPコードだけを成功判定にしません。

管理対象JWT境界の検証はdescriptorのendpoint hostと設定を照合するものです。実際のJWT認証をその場で試験することとは区別します。この検証器は descriptorType と inlineContent を読む別の形で、Control Planeの descriptors.*.data 方式へそのまま適用されるものではありません。

agent-safety / KYCで同じ名前が現れたら

agent-safety: ダッシュボードはAWS registryとレコードの列挙APIを持ちます。一方、/api/registry、予算・同期など独自の管理APIも併存しています。ローカルのAgent管理とAWSサービスを名前だけで同一視しないでください。ソース内の提供リージョン一覧は実装中の固定値であり、AWSの最新の提供状況を保証しません。

KYC Registry Proxy: 該当CloudFormationのDescriptionは「Lambda + API Gateway fronting DynamoDB」です。これはDynamoDBベースの別実装であり、AWS Agent Registryとの統合として数えません。

環境・権限の準備

プラットフォーム担当者の確認項目

Control Plane全体の起動・デプロイは Control Plane README と 開発者向けオンボーディング を参照してください。ここではRegistry固有の配線を確認します。

  1. AWS SDK・CLIがサービスモデルを持つか確認

    依存定義の下限はboto3 / botocoreともに1.43.0。実際の環境で agent-registry-control を扱えることを確認します。Terraformのregistryモジュールは aws agent-registry-control help の成功を検査します。

  2. 対象アカウント・リージョンを確認

    Control Planeの共有クライアントは settings.AWS_REGION を使用。GOVERN_AWS_REGION は監督対象fleetの設定であり、Registry接続リージョンと同じ意味ではありません。サービス利用可否は対象環境で確認します。

  3. Terraformでregistryを構築

    modules/agent_registry はAWS CLIで同名registryを探索して再利用、なければ作成します。既定名はAVA。CLIや作成の失敗ではエラーにする実装です。

  4. バックエンドへ出力値を接続

    ECSタスクの AGENT_REGISTRY_ID、AGENT_REGISTRY_ARN、AGENT_REGISTRY_NAME を確認。設定変更後は稼働タスクが新設定を受け取ったかも確認します。

  5. IAMと承認テーブルを確認

    ECSにはRegistry作成・読取・更新・承認・タグ・検索等の権限設定があります。AWS権限だけでなく、承認ポリシーと承認要求のDynamoDB設定・アクセスも必要です。

  6. 承認の初期ルールと運用を決定

    一致ポリシーがないと通常登録は自動承認へ進みます。手動承認を試す場合は名前パターン等が一致する有効ルールを作り、キュー生成とAWS状態を確認します。

初回登録の手順

小さな登録で一連の状態を確認する

画面から始める

  1. Control Planeにログインし、/registry を開きます。
  2. AgentsまたはSkillsのカタログを開き、Deploy to Registry で登録します。Custom Resourcesは Register custom resource から名前・kind・説明・タグを指定できます。
  3. 登録済み一覧の状態を確認します。active はAPPROVED、pending は詳細な status_raw の確認が必要です。
  4. 承認待ちならADMINが /operate/approvals で対象と理由を確認して判断します。
  5. 要求の状態とAWSレコードの状態が一致したことを確認します。
  6. テスト終了後、DeleteでDEPRECATEDへの変更を確認します。runtimeや接続先の削除は別操作です。

運用開始前に理解しておく境界

  • 複数人承認: quorumの値を保存しても、現行の承認処理は1回の判断で確定します。
  • 監査の完全性: 通常登録の自動承認経路はrequire_approval用キュー作成を通りません。成功hookは別途承認済み履歴を書きます。「すべての経路に同じキュー履歴がある」とは言えません。
  • 障害時の整合性: record作成・申請・承認・キュー保存は複数の呼び出しで、全体のrollback処理は共有登録フローにはありません。
  • 規模: 一覧の50ページguard、タグ取得の追加呼出し、ポリシーscanの継続未処理を確認します。
  • 再試行: UUID名の通常登録を再POSTすると新規レコードになりえます。成功hookのDeploymentId照合やApp Factoryの名前照合とは扱いが異なります。
