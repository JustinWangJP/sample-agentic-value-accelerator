# API を REST API に移し、接続元 IP をリソースポリシーで制限して、デプロイは deploy.sh が作る

Registry ポータルの API を、API Gateway HTTP API から REST API（REGIONAL）に移す。リソースポリシーで、接続元 IP を変数 `allowed_source_cidrs` の範囲に限る（Issue #61 の実装案 8）。この ADR は、[ADR-0003](0003-public-https-without-waf-and-single-registry.md) のうち HTTP API を選んだ部分と、防御を JWT authorizer と Lambda 内の検査だけに頼る部分を置き換える。WAF・VPC・NAT・独自ドメインを使わないこと、Registry を 1 つだけ使うことなど、ADR-0003 のほかの決定は変えない。

dev は、特定の IP から機能を確かめるための環境である。HTTP API にはリソースポリシーがなく、IP で拒否するには、リクエストが Lambda まで届いた後に確かめるしかない。REST API なら、リソースポリシーの明示的な Deny で、許可していない IP からのリクエストを Lambda より手前で拒否できる。

REST API は、経路を足しても、デプロイを作り直すまで利用者には反映されない。そこで、デプロイは Terraform ではなく `scripts/deploy.sh` が作る（仕様の案 A）。`management`・`decision` は、本体とは別の state から経路を足している（[ADR-0013](0013-separate-portal-addon-states.md)）。

| 対象 | 決定 | 理由 |
| --- | --- | --- |
| 認可 | `COGNITO_USER_POOLS` の authorizer を使う。各メソッドに `authorization_scopes = ["registry-portal/api.invoke"]` を付け、アクセストークンを受け付ける。リソースポリシーは、全体を Allow する文と、`NotIpAddress`（`aws:SourceIp` が `allowed_source_cidrs` 以外）を Deny する文の 2 つで作る | Cognito authorizer とリソースポリシーを併用すると、API Gateway はまず Cognito で呼び出し元を認証し、成功したときだけリソースポリシーを評価する。このとき明示的な Allow が必要で、Deny や「どちらでもない」は拒否になる（[公式文書](https://docs.aws.amazon.com/apigateway/latest/developerguide/apigateway-authorization-flow.html#apigateway-authorization-flow-cognito)）。仕様では評価の順を未確認としていたが、これで確認できた |
| 資源の所有（ADR-0013 との関係） | 本体は、REST API、リソースポリシー、authorizer、全スタックの経路のパスに当たるリソースの木、各リソースの `OPTIONS`、エラー時の応答（gateway response）、ステージ、ステージのメソッド設定、初回のデプロイ、本体の経路のメソッドと統合を所有する。`management`・`decision` は、自分の経路のメソッド・`AWS_PROXY` 統合・Lambda の呼び出し許可だけを所有する。リソースの ID は、`data "aws_api_gateway_resource"`（`rest_api_id` とパスで引く）で取得する。tfvars に転記する値は、`http_api_id`・`jwt_authorizer_id`・`management_integration_id` の代わりに、本体の output `rest_api`（REST API の ID・ステージ名・authorizer の ID・scope・CORS の許可リストをまとめたオブジェクト）にし、追加スタックは同名の変数でそのまま受け取る | REST API のパスはリソースの木で表し、同じ親の下に同じパスの部分は 1 つしか作れない。`/api`、`/api/records`、`/api/records/{recordId}`、`/api/records/{recordId}/deprecation-requests` は、複数のスタックの経路が共有する親である。そのため、どのスタックが作るかを 1 つに決める必要がある。HTTP API の route に当たるのは、パスとメソッドの組である。リソースを本体に集めても、「本体から同じ route を重ねて定義しない」という ADR-0013 の決定は保たれる。統合はメソッドごとに作るため、統合の ID を転記する必要はなくなる |
| デプロイ方式（案 A） | ステージは本体の Terraform が持つ。`aws_api_gateway_deployment` は、ステージを作るための初回のデプロイとしてだけ使う。`triggers` は付けない。ステージの `deployment_id` は `lifecycle { ignore_changes = [deployment_id] }` で Terraform の管理から外す。`scripts/deploy.sh` は、本体・`management`・`decision` を apply した後（追加スタックの撤去を含む）に、毎回 `aws apigateway create-deployment`（ステージを指定しない）で新しいデプロイを作る。続けて、`aws apigateway update-stage --patch-operations op=replace,path=/deploymentId,value=<ID>` で、ステージをそのデプロイに切り替える。本体の撤去の後は実行しない。REST API の ID とステージ名は、本体では output `rest_api` から、追加スタックでは検査済み plan の変数 `rest_api`（本体の output の転記）から読む。追加スタックには再デプロイ先を返すための output を持たせない | ステージの設定以外の変更は、経路・メソッド・統合・authorizer・リソースポリシーを含め、すべて再デプロイしないと反映されない（[REST API のデプロイ](https://docs.aws.amazon.com/apigateway/latest/developerguide/how-to-deploy-api.html)、[再デプロイが必要な変更](https://docs.aws.amazon.com/apigateway/latest/developerguide/updating-api.html)）。デプロイは、その時点の API 全体のスナップショットである。どのスタックを反映した後でも作り直せば、全スタックの経路とリソースポリシーがそろって反映される。`allowed_source_cidrs` を変えた場合も、本体の apply の後に再デプロイされる。そのため、ポリシーのハッシュを `triggers` に入れる必要はない。`update-stage` の `/deploymentId` の `replace` は公式に対応している（[UpdateStage の patch 操作](https://docs.aws.amazon.com/apigateway/latest/api/patch-operations.html#UpdateStage-Patch)）。指定した項目だけを変えるため、アクセスログやスロットリングの設定には触れない |
| ステージ名 | `v1` に固定する（変数にしない）。呼び出しの基準 URL は `https://{restapi-id}.execute-api.{region}.amazonaws.com/v1` になり、`VITE_API_BASE_URL` にも `/v1` を含める。Lambda の呼び出し許可の `source_arn` では、今と同じくステージを `*` にする | REST API の URL にはステージ名が入る（[REST API のデプロイ](https://docs.aws.amazon.com/apigateway/latest/developerguide/how-to-deploy-api.html)）。環境は API そのもの（`name_prefix`）で分かれていて、ステージは 1 つだけ使う。固定の名前にしておくと、URL と `deploy.sh` が扱う値が環境によって変わらない |
| CORS：`OPTIONS` | 本体が、各リソースに `OPTIONS` メソッドを作る。authorizer はなし（`NONE`）にし、`AWS_PROXY` で管理 Lambda に統合する。Lambda は、リクエストの `Origin` を許可リストと照合し、一致したときだけ CORS のヘッダーを付けて返す。許可リストは、CloudFront の origin（`local.spa_origin`）と `var.local_dev_origins` を合わせたもので、環境変数で Lambda に渡す | `Access-Control-Allow-Origin` には 1 つの値しか返せない。CloudFront と `local_dev_origins` の両方を許可するには、リクエストに応じて値を選ぶ必要がある。MOCK 統合の統合レスポンスでは、メソッドリクエストのヘッダーをパラメータマッピングの元にできない（[マッピング元の一覧](https://docs.aws.amazon.com/apigateway/latest/developerguide/rest-api-parameter-mapping-sources.html)）。照合は VTL のマッピングテンプレートに頼ることになり、その動作は公式文書では確かめられなかった（下の「未確認の事項」）。下の行のとおり、実際の応答の CORS ヘッダーは、どのみち Lambda が付ける必要がある。照合を Lambda の 1 か所にまとめれば、pytest で検証できる |
| CORS：実際の応答 | 管理 Lambda と決裁 Lambda は、すべての応答に、照合して一致した `Access-Control-Allow-Origin` と `Vary: Origin` を付ける。`decision` スタックには、許可リストを本体の output `rest_api` の `cors_allowed_origins` として tfvars で渡す | Lambda のプロキシ統合では統合レスポンスがないため、CORS のヘッダーはバックエンドが返す必要がある（[プロキシ統合の CORS](https://docs.aws.amazon.com/apigateway/latest/developerguide/how-to-cors.html#apigateway-enable-cors-proxy)）。HTTP API で CORS を設定している間は、バックエンドが返す CORS のヘッダーは無視される（[HTTP API の CORS](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-cors.html)）。そのため、移行の前に Lambda へ入れても動作は変わらない |
| CORS：エラー時の応答 | `DEFAULT_4XX` と `DEFAULT_5XX` の gateway response に、`gatewayresponse.header.Access-Control-Allow-Origin = method.request.header.Origin`（リクエストの `Origin` をそのまま返す）と `gatewayresponse.header.Vary = 'Origin'` を設定する。`Access-Control-Allow-Credentials` は付けない | 401（`UNAUTHORIZED`）、403（`ACCESS_DENIED`）、429 などの型は、個別に設定しなければ `DEFAULT_4XX` / `DEFAULT_5XX` の設定を使う（[gateway response の型](https://docs.aws.amazon.com/apigateway/latest/developerguide/supported-gateway-response-types.html)）。gateway response のテンプレートは VTL ではなく、単純な変数の置き換えしかできない。一方で、メソッドリクエストのパラメータは参照できる（[gateway response](https://docs.aws.amazon.com/apigateway/latest/developerguide/api-gateway-gatewayResponse-definition.html)）。許可リストとの照合はできないため、`Origin` をそのまま返す。固定値（CloudFront の origin）にすると、ローカルの SPA では 401 が CORS エラーに見え、仕様の受け入れ条件「未認証の 401 も SPA で判別できる」を満たせない。トークンは `Authorization` ヘッダーで送り、Cookie の資格情報は使わない。そのため、別の origin から読めるのはエラーのメッセージだけである。また、そこまで届くのは許可した IP からのリクエストに限られる。#73 の「CloudFront の origin と `local_dev_origins` の両方を許可する」は、Lambda が返す応答では許可リストとの照合で満たし、gateway response では照合せずに満たす。この点は仕様の文面と異なる |
| スロットリング | `aws_api_gateway_method_settings`（`*/*`）で、今と同じ値（10 rps、バースト 20）を設定する | ステージの設定は再デプロイなしで反映される（[REST API のデプロイ](https://docs.aws.amazon.com/apigateway/latest/developerguide/how-to-deploy-api.html)） |
| ログ | ステージの `access_log_settings` で、今のロググループ（`/aws/apigateway/${name_prefix}`）にアクセスログを送る。実行ログ（execution logging）は有効にしない | bootstrap の権限は、このロググループの名前を前提にしている。実行ログは費用が増えるわりに、dev の確認には要らない |
| `aws_api_gateway_account` | 本体ではなく bootstrap が持つ。API Gateway が CloudWatch Logs に書き込むための IAM ロール（信頼する主体は `apigateway.amazonaws.com`、AWS 管理ポリシーは `AmazonAPIGatewayPushToCloudWatchLogs`）と、`aws_api_gateway_account` を作る。どちらも bootstrap の変数 `manage_api_gateway_account`（bool、既定値 `false`）を `true` にしたときだけ作る。有効にする前に `aws apigateway get-account` を実行し、`cloudwatchRoleArn` がすでに設定されているか確かめる。設定されていれば `false` のままにし、その設定をそのまま使う | `cloudWatchRoleArn` はアカウントの設定で、リージョンごとに 1 つしかない（[CloudWatch へのログの権限](https://docs.aws.amazon.com/apigateway/latest/developerguide/set-up-logging.html#set-up-access-logging-permissions)）。同じアカウント・リージョンにある、ほかの REST API のログにも効く。AWS provider 6.71.0 では、この資源を destroy すると `cloudwatchRoleArn` を空に戻す（[provider のソース](https://github.com/hashicorp/terraform-provider-aws/blob/v6.71.0/internal/service/apigateway/account.go)の `Delete`。`reset_on_delete` は 6.0.0 で廃止された（[CHANGELOG](https://github.com/hashicorp/terraform-provider-aws/blob/v6.71.0/CHANGELOG.md)））。本体に置くと、dev の撤去（[ADR-0014](0014-dev-teardown-protection-and-scope.md)）のたびにアカウントの設定が消える。bootstrap は撤去の対象外である。既定値を `false` にして、既存の設定を黙って上書きしないようにする |

## 検討した選択肢

- **案 B（追加スタックごとにデプロイを作り直す）は採用しない。** デプロイは API 全体のスナップショットで、ステージは 1 つである。各スタックが、デプロイとステージの `deployment_id` を別々の state で持つことになり、plan のたびに互いの値を戻し合う。反映の順番によって、どの経路が公開されるかも変わる。
- **ステージもデプロイも Terraform の外に置く案（仕様の案 A の文面どおり）は採用しない。** アクセスログとスロットリングの設定が CLI の手順に移り、plan で確かめられなくなる。デプロイだけを外せば、案 A の狙い（全スタックの経路をそろえてから公開する）は満たせる。
- **リソースポリシーのハッシュを本体のデプロイの `triggers` に入れる案（#61 の実装案 8 と #73 の「ポリシーのハッシュを再デプロイの契機に含める」）は採用しない。** 仕様の文面とは異なる決定である。仕様の狙い（`allowed_source_cidrs` を変えて反映すると新しいポリシーが効く）は、`deploy.sh` が apply のたびに再デプロイすることで満たし、`tests/test_deploy.py` で確かめる。`triggers` は要らない。Terraform のデプロイを作り直すと、ステージから外したデプロイ ID と state が食い違うおそれもある。
- **`create-deployment --stage-name v1` でステージを直接切り替える案は採用しない。** 既存のステージに配るときの CLI の例はある（[AWS CLI の例](https://docs.aws.amazon.com/cli/latest/userguide/cli_api-gateway_code_examples.html)）。しかし、ステージのほかの設定がどう扱われるかは、公式文書に明記されていない。`update-stage` の `/deploymentId` の `replace` なら、変える項目がはっきりしている。
- **`OPTIONS` を MOCK 統合で処理する案は採用しない。** 理由は上の表の「CORS：`OPTIONS`」のとおり。
- **エラー時の応答の `Access-Control-Allow-Origin` を固定値にする案は採用しない。** ローカルの SPA で 401 を判別できない。
- **リソースを各スタックが作る案は採用しない。** 共有する親のリソースを、どちらの state が持つかが決まらない。
- **`aws_api_gateway_account` を本体に置く案は採用しない。** 撤去のたびにアカウント全体の設定が消える。
- **ステージ名を環境名（`dev`）にする案は採用しない。** 環境は API 自体で分かれている。環境ごとに URL の形が変わると、手順と output が複雑になる。

## 影響

- 経路・リソースポリシー・authorizer・gateway response の変更は、`scripts/deploy.sh` で反映したときだけ公開される。`terraform apply` を直接実行した場合は、手で再デプロイするまで公開されない。追加スタックを反映した後に、すべての経路を含むデプロイが作られることを `tests/test_deploy.py` などで確かめる（#74）。
- 追加スタックを撤去した後も再デプロイする。再デプロイしないと、ステージの古いデプロイに、撤去した Lambda への経路が残る。撤去の順番（追加スタック → 本体）は ADR-0014 のまま変えない。
- 許可していない IP から呼ぶと、トークンがない場合は 401（Cognito の認証が先に失敗する）、有効なトークンがある場合は 403 になる。どちらの場合も Lambda は起動しない。`OPTIONS` は authorizer がないため、許可していない IP からは 403 になる。dev での確認（#76）では、この 2 通りを分けて確かめる。
- バックエンドには、`OPTIONS` への応答と、すべての応答への CORS ヘッダーの付与（許可リストとの照合）が必要になる。仕様の「バックエンド」の項（#72）にはない作業である。HTTP API の間は、バックエンドが返す CORS ヘッダーが無視されるため、移行の前に入れても動作は変わらない。`OPTIONS` も管理 Lambda を起動するため、予約同時実行数（実装案 5）を決めるときは、プリフライトの分も見込む。
- 本体の output に、REST API の ID、ステージ名、authorizer の ID、scope、CORS の許可リストをまとめた `rest_api` を加える。追加スタックは同名の変数 `rest_api` で受け取り、値を個別に転記しない。`VITE_API_BASE_URL` には `/v1` を含める。追加スタックの tfvars と Terraform ガイド 4.3 を、新しい転記項目に合わせて直す。
- 本体を反映する permission set（bootstrap の `HttpApi` の文）の対象を、`/apis` から `/restapis` と `/restapis/*` に変える。再デプロイ（`POST /restapis/{id}/deployments`、`PATCH /restapis/{id}/stages/v1`）も、この範囲に含まれる。
- dev の HTTP API にすでに追加スタックの route がある場合も、追加スタックは撤去しない。本体を反映した後、追加スタックの tfvars を書き換えて反映する。HTTP API と一緒に削除された route は、追加スタックの plan の refresh で state から外れる（AWS provider は、見つからない資源を state から外す）。旧 HTTP API 向けの Lambda 呼び出し許可は、REST API 向けの許可に置き換わる。本体の反映から追加スタックの反映までの間は、追加スタックの経路を利用できない。手順は Terraform ガイドの「HTTP API から切り替える」に従う。
- REST API のリクエスト単価は、HTTP API より高い（100 万件あたり $3.50 と $1.00）。この利用量では、月に数セントにとどまる。
- 反映前ガード（`scripts/check_plan.py`）、`tests/*.tftest.hcl`、経路の権限テストを、REST API の資源に合わせて直す（#73・#74）。

## 未確認の事項

- gateway response のヘッダーで `method.request.header.Origin` を参照したとき、リクエストに `Origin` がない場合と、メソッドリクエストでそのヘッダーを宣言していない場合の動作。公式文書では、メソッドリクエストのパラメータを参照できることまでしか確かめられていない。dev で確かめる（#76）。
- MOCK 統合の統合レスポンスのテンプレートで、`$input.params('Origin')` がメソッドリクエストのヘッダーを返すかどうか。採用しない案の判断材料であり、決定には影響しない。
- 同じ親の下に、固定のパス（`/api/records/publication`）とパスパラメータ（`/api/records/{recordId}`）があるとき、REST API が固定のパスを優先するかどうか。HTTP API では優先されることを確認済みだが、REST API については公式文書で確かめられていない。dev で確かめる（#76）。
- `cloudWatchRoleArn` を設定していないアカウントで、`access_log_settings` を持つステージを作ると失敗するかどうか。
- 再デプロイのたびに古いデプロイが残る。1 つの API に残せるデプロイの数の上限は確かめていない。
