# 下書きの定義は custom descriptor を正本とし、補助テーブルには写しを置く

custom Agent の下書きでは、目的・接続先の参照・認証方式・連絡先・利用条件を、Registry レコードの custom descriptor（`descriptors.custom.data`）に canonical JSON として保存し、これを正本とする。連絡先・利用条件・接続先の参照は、補助テーブルの管理情報（`sk` = `MANAGEMENT`）にも写しとして保存する。この写しは、公開承認（#10）で公開版スナップショット（ADR-0007）を作るためだけに使い、下書きの表示や編集には使わない。所有チームだけは、引き続き補助テーブルを正本とする（ADR-0002）。

Registry レコードの定義は Registry を正本とする（ADR-0002）。連絡先・利用条件・接続先の参照も Agent の定義の一部であるため、定義から外して補助テーブルだけに置くと、Registry の版と定義が食い違う経路ができる。一方、ADR-0007 が避けたのは、検索に使わない値で custom metadata の schema を広げることである。descriptor に置くことは ADR-0007 の判断と矛盾しない。

## 検討した選択肢

- 連絡先・利用条件・接続先の参照を補助テーブルだけに置き、descriptor から外す案は採用しない。Registry の版だけでは定義を復元できなくなるうえ、descriptor を直接読む利用者（AWS コンソールや発見 API）に定義の一部が見えなくなるためである。
- custom metadata に置く案は、ADR-0007 のとおり採用しない。

## 影響

- 写しが正本と食い違った場合は、内容ハッシュに写しを含めているため更新が 409 になる。再読み込みして保存すると、写しも正本に揃う。
- descriptor の中身が Registry の意味検索の関連度に使われるかどうかは、AWS の[検索の資料](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/registry-search-records.html)に明記がない。使われる場合、連絡先などの語でも Agent が検索に当たる。これらは公開承認後にカタログの詳細で全員に表示する値なので、検索に当たっても公開範囲は広がらない。秘密情報はフォームに入力させない（参照だけを記載する）。実環境で検索結果を確認し、問題があればこの ADR を見直す。
- 公開承認（#10）は、公開版スナップショットを descriptor（正本）から作るか写しから作るかを決めるとき、写しが正本と一致することを内容ハッシュで確認する。
