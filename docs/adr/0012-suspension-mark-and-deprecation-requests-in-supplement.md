# 公開停止の印と廃止依頼は補助テーブルに置き、AWS の状態を優先する

[ADR-0002](0002-registry-as-source-of-truth.md) は、Registry レコードの状態を AWS だけを正本とし、独自の承認状態を持たないと定めている。補助テーブルには、Registry に保存できない情報だけを置く。公開停止・廃止・廃止依頼（#13）では、補助テーブルに置くものとして次の2つを加える。

- **公開停止の印**: 管理情報の `suspendedVersion`。値は、公開停止した時点で公開中だった版。
  - 公開停止は AWS では却下（`REJECTED`）であり、状態そのものは AWS が持つ。
  - ただし AWS の状態だけでは、「公開停止して発見できない」と「新しい版を却下したが、旧版は公開中」を区別できない（二重リビジョン）。印は、この区別のためだけに使う。
  - 公開停止の成功で書き、ポータルでの公開承認の成功で消す。
- **廃止依頼**: 依頼の正本（主体・理由・日時）と、その状態（未解決・解決済み）、解決の記録（廃止か見送りか・理由・主体・日時）。
  - 廃止依頼は AWS の状態を変えないポータル内の依頼で、Registry には保存先がない。申請スナップショットと同じ位置付けで扱う。

どちらも AWS の状態を上書きしない。

- 印が残っていても、AWS が公開中（`APPROVED`）を返していれば、公開中として扱う。ポータルの外で再承認された場合（ADR-0001 の想定外の経路）に、残った印で「公開停止済み」と誤表示しないためである。
- 廃止依頼の状態は、レコードの状態ではない。廃止は AWS の `DEPRECATED` で判断する。

## 検討した選択肢

- **印を持たず、AWS の `REJECTED` と公開版の有無だけで判断する案は採用しない。** 二重リビジョンで新しい版を却下した場合と、公開停止とを区別できない。公開中の版を誤って「なし」と表示するか、公開停止中のレコードを公開中と表示することになる。
- **AWS の `statusReason` に公開停止を示す値を埋め込む案は採用しない。** `statusReason` は Curator が入力した理由をそのまま送る項目である（ADR-0010）。機械的な判別に使うと、理由の文言と判別の規則が衝突する。
- **廃止依頼を AWS の状態（例: 依頼を受けたら `DEPRECATED` 以外へ遷移）で表す案は採用しない。** 依頼は Curator の判断前の要望であり、公開中のレコードの発見可否を変えてはならない。

## 影響

- 印は、ポータルの公開承認でしか消えない。ポータルの外で再承認された後に Publisher が新しい版を作ると、その版の審査中は印が残る。この間は公開中の版がないものとして扱い、公開停止を受け付けない。廃止はできる。
- 補助テーブルの廃止依頼が失われても、AWS の状態は正しく残る。失われるのは依頼の記録と、審査待ちの一覧への表示だけである。
