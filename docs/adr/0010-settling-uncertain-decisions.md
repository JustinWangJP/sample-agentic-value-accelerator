# 結果確認中の決裁は、決裁 handler の再送と、決裁した Curator の操作照会で確定する

設計書「内容を確認してから決裁する」は、AWS の結果が分からない書き込みを「結果確認中」として記録し、正本を再取得して確定することを定めている。決裁（公開承認・却下）は、確定の経路を次のとおりに限る。

- **再送（決裁 handler）**: Curator が同じ `Idempotency-Key` と同じ本文で再送すると、同じ操作として現物から結果を確定する。AWS の呼び出し（または受け付けの確認）まで至らなかった操作には、意図に記録した同じ決裁（種別・理由）を送り直す。先の呼び出しが AWS に届いていた可能性があるため、送り直しのエラーでは失敗と確定しない。
- **操作照会（管理 handler、`GET /api/operations/{id}`）**: AWS を呼び直さず、観測できる状態（`APPROVED` / `REJECTED`）からだけ確定する。管理 Lambda の実行ロールには決裁の権限（`UpdateRegistryRecordStatus`）を与えないためである（設計書「最小インフラとセキュリティ」）。決裁の操作を参照できるのは、その決裁を行った Curator 本人に限る。下書きの操作を所有チームの Publisher に限るのと同じく、操作の主体以外に結果確認中の決裁の中身と確定の契機を渡さないためである。

決裁理由は、公開承認・却下の両方で必須とし、AWS の `statusReason`（0〜255文字）にそのまま送れるよう255文字以内とする。ポータルの操作記録（`AUDIT#…#INTENT`）にも同じ値を残す。

## 検討した選択肢

- 操作照会でも決裁を送り直す案は採用しない。管理 Lambda に決裁の権限が必要になり、決裁 handler だけが状態を遷移させるという IAM の境界（ADR-0001）が崩れる。
- 決裁の操作を Curator なら誰でも照会・確定できるようにする案は採用しない。決裁した Curator が不在のときにロックが残り続けるおそれはあるが、その回復は Admin の回復操作（設計書「ロールと所有」）で扱う。
- 公開承認の理由を任意にする案は採用しない。Issue #10 の受け入れ条件「公開承認にも理由を記録する」と、設計書の API 表「理由とスナップショットのハッシュを検査して公開承認する」に合わせる。
- 決裁理由をポータルだけで長く保存し、AWS には切り詰めて送る案は採用しない。ポータルと AWS で記録された理由が食い違う。

## 影響

- 決裁した Curator が結果確認中のまま不在になると、そのレコードへの書き込みは Admin の回復操作まで止まる。
- 結果確認中の決裁を他の Curator が確定させたい場合は、決裁した Curator に同じキーでの再送を依頼する。
