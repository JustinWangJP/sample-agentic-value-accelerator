01 / 対象と使い方

本資料は既存のオンボーディング入門を補う設計・保守資料です。管理者・基盤担当・アプリ開発者が、変更の影響範囲と確認手順を共有するために使います。

領域責務・境界本資料の深さ
plan/価値検討、導入・設計ガイド入口と役割のみ
platform/control_plane/管理UI/API、配備、セキュリティ、観測・統制IaCと主要コードを確認した中心対象
applications/fsi_foundry/共通foundationsと金融向けユースケース共通基盤との接続と改修手順。個々の業務アルゴリズムは個別READMEを参照
applications/reference_implementations/用途ごとに独立性のある参照実装各実装の設計は統一しない。配備前に固有のREADME/IaCを読む
applications/app_factory/生成処理・UI雛形Control Plane側の申請APIとの境界を示す
情報の読み方：「実装確認」はソースやIaCに定義があることを意味し、稼働や業務要件の充足を保証しません。「受入確認案」「推奨運用」は継続開発向けの提案です。実環境のリソース一覧、性能、費用、障害復旧時間は未計測です。

02 / インフラアーキテクチャー・AWS構成図

フロント配信とAPI入口は別系統です。CloudFrontのオリジンはS3であり、ローカルnginxの/api/プロキシ構成をそのままAWS配備図に当てはめません。API GatewayはVPC Link経由でECSモジュールのALBリスナーをHTTP_PROXY統合します。

構成要素定義・役割変更時の確認
ネットワークnetworking/main.tf：VPC、public/private subnet、IGW、NAT、経路既存VPCを使う条件とCIDR重複、AZ、NAT費用・経路
API実行基盤ecs/main.tf：クラスター、タスク定義、Service、内部ALB、IAM、ログCPU/メモリ、タスク数、SG、/health、ECRイメージ
API入口api_gateway/main.tf：HTTP API、VPC Link、統合・ステージ、ドメインリスナーARN、ステージとROOT_PATH、CORS・DNS
UI配信cloudfront/main.tf：S3 OAC、Distribution、SPA用エラー応答、DNSキャッシュ更新、ビルド時API接続先、証明書リージョン
保護・認証waf/main.tf / cognito/main.tfWAFはCLOUDFRONTスコープ。API全経路への保護を推定しない
永続化dynamodb/main.tf / s3/main.tfキー/GSI、保持・暗号化・復旧設定、共有データへの影響
配備基盤step_functions/main.tf / codebuild/main.tf実行IAM、失敗分岐、ビルド入力・出力、成果物権限
関連・拡張モジュールルートmain.tf：Agent Registry、Harness実行Role、Service Approval、Frontier Pipeline、観測などモジュールの存在と、当該環境への実配備を区別

新規VPCと既存VPC

ルートIaCはvpc_idが空でなく、public/private両方のsubnet配列が存在すると既存VPCを使用します。それ以外はnetworkingモジュールの作成経路です。既存VPCを指定するときはIDだけを埋めず、subnet・ルーティング・到達性も揃えてください。

条件付き構成

CodeCommitはenable_codecommit、サンプルデータレイクはenable_sample_datalake、X-Ray Transaction Search関連はenable_xray_transaction_searchが作成条件です。Docker Hub認証のSecretはユーザー名とトークンが両方ある場合に作成されます。各フラグの実際の値はtfvarsとplanを確認してください。

根拠：ルートmain.tf、variables.tf、providers.tf、上表のモジュール。図は主要要素を示しており、全IAMポリシーや全サブリソースを列挙したものではありません。

03 / ネットワーク・認証・権限の境界

ネットワーク設計で誤解しやすい点

確認したECSモジュールではALBはinternal=trueですが、ALBとECS Serviceのsubnet指定はpublic subnet、タスクはassign_public_ip=trueです。public IPの割当だけで通信が許可されるわけではなく、SG・経路・入口構成を併せて評価します。private subnetへ変更する場合は、イメージ取得・ログ送信・AWS API・外部HTTPの到達経路をまとめて検証します。

ユーザー認証とAPI認可

  1. ブラウザで認証し、トークンをAPIへのリクエストに付与します。Cognitoと外部IdP設定は別途確認します。
  2. security.verify_tokenはJWTのkidを読み、Cognito公開鍵を取得・キャッシュし、RS256、audience、issuer、有効期限を検証します。鍵ローテーション時の再取得経路もあります。
  3. rbac.pyにはViewer=0、Operator=1、Admin=2の階層があり、ルート側の依存関係で必要ロールを要求します。JWT検証経路が複数あるため、認証改修では両方のテストを対象にします。
  4. 開発認証はENVIRONMENT=productionでは禁止する判定があります。実環境がproductionとして起動していることも配備時に確認します。
権限主体用途レビュー観点
利用者JWT/ロール管理APIの閲覧・操作各ルートの依存関係、401/403、ロール不足時の拒否
ECS task execution roleコンテナ起動等タスク内アプリのAWS操作権限と混同しない
ECS task roleAPIからDynamoDB、S3、AgentCore等へ接続追加したAPIに必要な最小権限と対象ARN
Step Functions / CodeBuild roleワークフローとビルド・IaC実行配備先アカウント、assume role、成果物、Secretアクセス
業務エージェント実行role実行時モデル・ツール・データアクセス管理基盤の権限を業務実行にそのまま流用しない

Discovery URLや外部HTTP、JWKSの取得失敗はネットワークとセキュリティ双方の境界です。単にタイムアウトを増やす前にsafe_fetch.py、認証設定、DNS、許可CIDR、エラー種別を確認します。具体的なルートの認可条件は実装を正としてください。

Foundryを変更するときの単位

共通基盤はapplications/fsi_foundry/foundations/、業務コードはuse_cases/、UIは対応するui/を起点にします。Quick Deployのapplications.pyは選択したパターンのIaC、shared、Dockerビルド用コード、共通src、ユースケースsrc、存在すればUI等をZIPへ収録します。新しいファイルを追加したときは、ローカルで存在するだけでなく成果物にも含まれるか確認します。

代表APIのURLを調べる

設定の既定API_PREFIXは/api/v1、ROOT_PATHは空です。実際のURLはmain.pyのマウント、ルーターのprefix、関数デコレーターのパスを合成して確認します。第7章の操作パスは最後の部分のみを示します。稼働環境のOpenAPIを取得できる場合は、そちらとフロントの接続先も照合してください。

06 / デプロイ方式・処理フロー

Foundry Quick Deployを追う

  1. applications.pyのdeploy_foundry_use_caseがOperatorロール、ユースケース、framework、patternを検証。
  2. foundation-stackの出力と入力パラメータを合成。基盤が見つからない場合の警告経路を持つ。
  3. LangfuseやGateway仮想キーを条件付き準備。Gateway準備に失敗して直接Bedrockへ進むフォールバックがあるため、配備成功だけで接続経路を断定しない。
  4. DeploymentCreateから記録を作成し、対象ソースをZIPにしてS3へアップロード。
  5. PipelineServiceのstart_pipelineはテンプレートのonboarding jobを取得し、入力を構成してStep Functionsを開始。jobがなければValueError。実行ARNを返す。
  6. state machineとCodeBuildが後続処理を担当。状態、ビルド、出力、失敗記録を確認して完了を判断。

基盤自体の配備

deploy-full.shはTerraform、バックエンドイメージ、Service Approval Runnerイメージ、ECS更新、カタログseed検証、フロントbuild・配信、Cognitoユーザー作成等を段階実行します。実行前にscripts/README.mdとスクリプトの引数・環境変数を確認してください。

推奨する変更ゲート：対象アカウントとリージョン確認 → 現状output/イメージ/設定の記録 → planレビュー → 適用 → API疎通 → 認証・主要画面 → 実行状態と出力 → ロールバック可能性の確認。deploy-full.shは実際に変更を加える処理です。本資料の作成では実行していません。

失敗の切り分け順

deployment ID → Step Functions execution ARN → 失敗ステートと入力 → CodeBuild ID・ログ → Terraform/ビルドのエラー → ECSイベント・ログ／対象サービスの出力、の順で辿ります。入力・ビルド・IaC・アプリ起動を同じ「配備失敗」にまとめないことで、再実行の安全性を判断できます。

09 / 管理・運用・復旧手順

事象まず確認するもの対処と完了条件
UIだけ表示できないCloudFront/S3の配備ファイル、ブラウザconsole、API接続設定buildと配信対象、キャッシュを確認。画面表示とAPI要求の両方が正常になること
APIが応答しないAPI Gatewayログ、VPC Link、ALB /health、ECS Service・ログ統合先/パス/SG/タスク起動を順に確認。/pingと認証付きAPIを分けて検証
401/403JWT有効期限、issuer/audience、JWKS取得、role再ログインだけで解消しなければネットワーク・設定・権限を確認。権限不足は拒否のまま維持
フリート表示が空・過少対象アカウント、GOVERN region設定、取得ログ空を成功と断定しない。対象と出典、部分失敗を確認して再収集
配備が進まないdeployment ID、実行ARN、CodeBuild ID、失敗ステート失敗原因と既作成資源を確認後に再実行。二重作成と孤立資源を避ける
Gateway/モデル不調Gateway health、認証期限、model access、region、設定認証更新後にコンテナ・設定を反映。選択モデルの実呼出しで完了確認
変更後に障害直前のimage、UI artifact、設定、plan、migrationまず互換性を確認して戻す。アプリimageを戻すだけでデータ/IaC変更が戻るとは限らない

復旧対象を分けて管理する（推奨運用）

  1. コード：基準コミット、ECR image digest、UI配布物の版を記録。
  2. 管理データ：DynamoDBのPITR・バックアップ適用範囲をテーブル単位で確認。復元先テーブルを作る場合は設定・IAMの切替も手順に含める。
  3. IaC：state S3の版、lock、backend設定を記録。stateだけの巻き戻しは実リソースと不整合を作るため、差分を確認して復旧する。
  4. 設定・秘密：Secret値を資料へ記載せず、ARN、管理責任、更新手順を保持する。
  5. 検証：復旧後は疎通、認証、カタログ、状態参照、必要なモデル呼出しを確認し、RTO/RPOを実測して運用基準へ反映。

引継ぎで揃える環境情報

AWSアカウント、管理・対象リージョン、利用ドメイン、Terraform backend、tfvarsの保管場所、ECS Service、ECR image、各テーブル/バケット、配備ワークフロー、監視の通知先、権限の管理責任者を環境台帳に記録してください。これはコードだけでは確定できない実環境情報です。

変更時に資料も更新する

API追加は第7章へ行を追加し、役割・代表操作・確認観点を更新します。AWSリソースや接続変更は第2・3章の図と表、データや設定変更は第5章、配備や復旧変更は第6・9章へ反映してください。図には簡略化した範囲と条件付き構成を残し、解析日・基準コミット・確認済みテスト結果も合わせて更新します。
